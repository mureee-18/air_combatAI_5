# 仮説の書き方（立案方針）

ダッシュボードの「改善セッション」タブはこの方針を毎回表示し、事実カードと「いま実行するコマンド」の
間に置く。仮説は 1 行で書き、数値を 1 つだけ入れる。

## 書き方の型

```
[事実] の結果 [原因] が見つかったため、[変数] を [A] から [B] に変えると
[指標] が [現在値] から [目標値] になる
```

実際には 1 行の日本語でよい。原因は数値の予測を両方書く。

- 事実: 事実カードから 1 つ選ぶ（出典が隣にある）
- 原因: 変更前に決める。ログで裏を取りたいものは assumption として別途登録
- 変数: 1 つだけ
- 予測: 2 つ（挙動指標 1 つ、判定指標 1 つ）

## 必ず守ること

1. **1変数だけ**。同時に 2 つ変えると、悪化時に原因を切り分けられない。
2. **毎回ベースラインへ戻す**。前回の変更を残したまま次の変数を足さない。
2. **数値予測を書く**。「何を何倍にするか」が書けないなら変更しない。
3. **出所を付ける**。`--source` は「どこから見たか」（log / analysis / code / official）。
4. **判定はペア評価**。`avg_score` / `avg_our_alive` / `avg_enemy_alive` と win-draw-loss だけで見る。
   勝率では判断しない。`avg_score` が 0.5 を超えて初めて改善。
   採用判定は seeds 1-3 に加え未見 seed（4-6 等）でも検証する。適合seedのみの改善は過適合のため不採用（N-041）。
5. **1 戦で先に確かめる**。大量の戦を回す前に `verify --games 1` で意図した挙動が出るか見る。
6. **ログ構造を調べ直さない**。`tools/battle_analyzer/BATTLELOG_FORMAT.md` に既知の制約がある。
7. **測れないものは推測しない**。できないことを `assumption`（`--source code`）として残す。
8. **外したら理由を書く**。`record` の `--verification` に実測値と外れた理由を書く。

## 改訂サイクル（1変数・ベースライン復帰・ホールドアウト）

1 変数ずつ試す。複数変数を積み増さない。前回の変更が残ったまま次の変数を足さない。

1. **ベースラインへ戻す**（毎サイクルの最初）
   - args.json を採用済みベースライン（escortFireMinKm=35.0, fireRangeKm=50.0, trackConfirmFrames=0, roleSplit=0, evadeCrankDeg=0.0, escortFlankDeg=0.0, threatEvadeMaxFrames=0）に戻す
   - `python scripts/build_submission.py --deploy`
2. **1 変数だけ実装する**（args.json の値 1 つ、またはコード修正 1 箇所）
3. **1 戦ゲート**
   - `docker exec atla5-cpu bash -lc "cd /workspace && python validate.py --youth 1 --num-validation 1 --visualize 0"`
4. **seed 固定ペア評価**（seeds 1-3 × 両面）
   - `docker exec atla5-cpu bash -lc "cd /workspace && python /repo/local_test/run_eval_paired.py --seeds 1,2,3 --colors both --label <label> --out /workspace/paired/<label>.json"`
5. **ホールドアウト**（未見 seed 4-6 × 両面）
   - `docker exec atla5-cpu bash -lc "cd /workspace && python /repo/local_test/run_eval_paired.py --seeds 4,5,6 --colors both --label <label>_ho --out /workspace/paired/<label>_ho.json"`
6. **判定**
   - seeds 1-3 と 4-6 の両方で `avg_score` / `avg_our_alive` / `avg_enemy_alive` を比較する
   - どちらかで悪化したら即 revert し、採用しない
7. **記録**
   - `python analysis/tools/improvement_session.py validate --specialist default --paired /workspace/paired/<label>.json`
   - `python analysis/tools/improvement_session.py record ...`

改善しない変数は args.json とコードの両方をベースラインへ完全に巻き戻す。
試験済みの軸は「検証済みの変数軸」表へ 1 行足す。

```
# 例: ベースラインへ戻して 1 変数だけ試す
python scripts/build_submission.py --deploy
docker exec atla5-cpu bash -lc "cd /workspace && python validate.py --youth 1 --num-validation 1 --visualize 0"
```


## 深掘りと仮説の対応（CRITICAL — 深掘りの結論から仮説を逆算する）

深掘り（`deepen`）は事実カードの `summary` を具体的な分析結果に更新する。
**登録する仮説は必ずその深掘りの結論から立てる。** 深掘りと仮説が別軸だと、
検証しても深掘りの検証にならない（2026-10-15 ユーザー指摘）。

### 深掘りの型

1. **分布・時系列を数値で取る**（trajectory / battle_stats で距離・タイミング・機体別内訳）
2. **物理的制約を確認する**（初期残弾・補給なし・センサ距離・シナリオ上不可能な目標）
3. **コードに当たる**（該当ロジックを読み、原因を `default.py:行番号` まで特定する）
4. **結論を1文で書く**（「〜が原因。〜すべき」まで具体的に）

深掘り結論が「物理的制約で達成不能」なら、そのカードは見送り維持。
結論が「実装の問題」なら、そこが仮説の変数になる。

### 仮説の型（深掘り対応）

```
[深掘りした事実] の結果、[深掘りで特定したコード上の原因（file:line含む）] ため、
[その原因を直す1変数の変更] とすると、[挙動指標] が [現在値] から [目標値] に
なり、[判定指標] と予測する。
```

- **出所は `code`**（深掘りで実装を特定した場合）
- **変数は「コード変更」でもよい**（1変数ルールは「変数が1つ」であって「args.json の値」に限らない。
  例: `trackConfirmFrames` のような新規条件）
- **args.json のノブが検証済み軸なら、その軸の仮説は立てるな**（下の「検証済みの変数軸」参照）

### 深掘り→仮説の対応例

| 深掘り結論 | 仮説の変数 |
|---|---|
| 実装の問題（例: ターゲット再選択に追跡継続性がない） | コード変更（例: trackConfirmFrames） |
| 物理的制約（例: 30発目標は補給なしで不可能） | 仮説なし（見送り維持） |
| 既に検証済みの軸（例: fireRangeKm） | 仮説なし（別軸を探す） |

## 報告ルール ①②③

- ①は正味の**採用改良**のみ。変更→巻き戻しは変化なし。
- ②は検証済み仮説の**受容**のみ。棄却・登録だけは変化なし。
- ③は指標の新設・見直し＋軸整備＋定期整理。**測定値単体は変化なし**。
  値から変更（指標化・環境化・軸表化）を施して初めて③の変化とみなす。
- 同一材料：同じ状態なら止める／違う状態なら別形で立てる／無意味なら③。
  ②不在自体が③のトリガー。でっち上げは禁止。
- 毎報告で①②③の少なくとも1つに実質変化。
- commit は対象一覧＋文案を提示（明示指示時は提示後即実行）。マージは明示指示のみ。
- コピー釦経由の指示は確認なしで即実行。改善は1変数ずつ。

## 仮説が使う指標

判定指標は 2 つだけ。

| 指標 | 意味 | どこで見るか |
|---|---|---|
| `avg_score` | 自陣営スコアの平均。0.5 を超えると改善 | 評価タブ / `workspace/paired/<label>.json` |
| `avg_enemy_alive` | 敵の生存機数の平均。減らせていれば敵を倒せている | 同上 |

補助指標（原因究明用）。

| 指標 | 意味 | どこで見るか |
|---|---|---|
| `first_launch_lag` | 初探知から初発までの空白。長いほど攻撃機会を逃している | 自機視点タブ |
| `launch_count` | 総発射数。0 なら発射できていない | 自機視点タブ |
| `min_dist_km` | 最短交戦距離。近ければ射撃が楽 | 自機視点タブ |
| `fire_orders` | 射撃指示回数。発射数との差が制約の証拠 | ログタブ |
| `fire_conversion` | 発射転換率（発射÷指示）。内訳から変数・方向・数値予測入りの具体仮説文がカードの hypothesis 欄に自動生成される（閉鎖済み軸は繰り返さない）。量自体は勝敗を決めないため目標値なし | 評価タブ |
| `wipe_count` | 全滅戦数（自機生存0）。平均生存数が良くても完敗混じりでは採点が崩れるため tail risk の目安。0 のときはカード非表示 | 評価タブ |
| `stranded_ammo` | 死蔵弾数（撃墜機の持ち去り）。実測は『護衛用予備(escortReserveMsls)×到達前撃墜数』に一致。予備は勝ち筋のため0は設計上未達、減らす材料は生存＝護衛戦闘機の先行排除（winpath-escort）。0なら非表示 | 評価タブ |

## 定期整理（③ルーティン）

勝敗を動かすのは護衛対象機の撃墜（勝ち）／自機の生存（負け回避）のみ。
TIMEUP の引き分けでは敵戦闘機の撃墜数・接近距離・警報数は採点に影響しないため、
改善に効かないことが確認できた指標は仮説タブのカードから外す。
削除は定義の除去だけで計算は残し、いつでも戻せる。ペア評価の A/B 比較ロジックには触れない。

削除済み:
- `avg_enemy_alive`（カードのみ除去）… 引き分けでは敵生存 1〜5 でも一律 0.5。負けは負け。
- `pre_launch_threat`（カードのみ除去）… 大小どちらの分岐も手出し不可（lag 軸閉鎖）。
  N-034 の監視は `first_launch_lag` カードの自動分岐が継続（計算自体は残る）。
- `threat_frames`（カードのみ除去）… MWS（被弾警報）の探知距離は仕様側センサで約10km固定、
  判断周期も baseTimeStep=1.0s で最小のため、agent 側の 1 変数では短縮できない（O-083）。
  被弾警報フレーム数は採点に影響せず、この材料から生存軸の新規仮説は立てない。
- `detect_duty`（カードのみ除去）… 探知フレーム割合は主に開幕〜終盤の幾何（敵が射程外）で決まり、
  方位という 1 変数では動かせない。方位保持の形態（N-051）は交戦を減らし `avg_enemy_alive` を
  悪化させスコア不変（O-088）。識別可否の条件指標であり、単独では改善軸に使わない。

## ③のトリガー（いずれかがあれば着手）

- 新規材料：値変化・新規戦で未処理が出たら、その誘導・証拠の欠陥を修正
- 未処理の蓄積：増えたら優先度付きで処理
- 新規 seed 群：停滞時は未見 seed で汎化確認（s456 の前例）
- 健康診断：指標が現行データで解決するか確認（壊れた補完の検出）
- ユーザー指摘：摩擦点は即③化
- 上記のいずれも無ければ申告して止める（でっち上げ禁止）

目標の解除:
- `ammo_reserve` の目標 8 を解除（参考値化）。温存への誘導は N-028 で棄却済みのため、
  `stranded_ammo`（目標 0 維持）と合わせても保存戦略を処方しない。数値自体は残す。
- `min_dist_km` の目標 25 を解除（参考値化）。接近距離は引き分けで採点に影響せず（上記 79-81 行）、
  接近を深める変数（fireRange/break/beam）は全て棄却・接近軸は N-029 で閉鎖済みのため、
  未達表示を摩擦として残さない。数値とカードは診断用に残す。

独自の指標は `python tools/state_dashboard/add_metric.py` で追加すると、
評価タブの「独自指標」に現れる。

## 仮説の登録

```bash
python analysis/tools/improvement_session.py hypothesis "<上の型で書いた仮説>" \
    --specialist default --source log
```

1 サイクルにつき 1 件だけ登録する。複数登録するとどれが効いたか分からなくなる。

## 検証の前に「変数を変えたか」を確認する（CRITICAL）

`validate` は**変更後にのみ**意味を持つ。args.json もコードも変えていない状態で
ペア評価を回しても、前回と完全同一の結果になるだけ（2026-10-15 実測: N-120/N-123/N-124 が
いずれも avg_score 0.500 / our 3.0 / enemy 3.17 で全一致）。

1. 仮説を登録したら、**その変数を実際に変える**（args.json の値 or コード修正）
2. `verify --games 1` で意図した挙動が出るか確認
3. `validate` でペア評価
4. 変えていないなら validate せず、次の仮説を立てるか実装に着手する
